# 告警外发

检查告警链路：**有没有告警**、**发到哪**、**有没有把敏感信息一起发出去**。

## 一、何时用

- 上线前自检
- 应急演练前（「出事时谁会知道？」）
- 安全审查、等保准备

## 二、它查什么

| 级别 | 项 | 为什么 |
|---|---|---|
| 🔴 高 | **告警内容里带敏感信息** | 告警走第三方通道，管控更弱 |
| 🔴 高 | **webhook 用明文 http://** | URL 里通常就带着 access_token |
| 🟡 中 | 把带密钥的告警 URL 打进日志 | 日志长期留存，等于扩散发送权限 |
| 🟡 中 | 找不到任何告警/上报配置 | 出事没人知道，只能等用户投诉 |

## 三、为什么「告警」也是安全问题

告警常被当成「运维的事」，但它有个**安全属性**：

**告警通道通常是整个系统里管控最弱的一条出口。**

```
你的数据库：内网、有审计、有权限控制
你的告警 webhook：一个 URL，谁拿到谁就能发
```

所以「把 err.stack / req.body / 用户数据塞进告警」这件事，
等于**把敏感信息复制到一个管控更弱的地方**。

## 四、正确做法

```
❌ post(webhook, { text: err.stack + JSON.stringify(req.body) })
✅ post(webhook, { text: `[ERROR] trace=${traceId}` })   // 细节留在内部面板
```

**只发摘要 + trace id**，细节放在有权限控制的地方。

## 五、怎么用

```bash
<cli 路径> --demo
<cli 路径> --list-rules
<cli 路径> --html r.html
```

## 六、边界

- **不验证告警真的能发出去** —— 只看配置与代码。
- **「找不到告警配置」是弱信号** —— 可能由部署层（云监控、K8s 探针）统一做。
  报出来是提示你确认，不是断定你没做。
- **不检查告警的时效与去重** —— 那是 SRE 范畴。
- 与 `dsh-cn-log-retention` 分工：那个查日志留多久，这个查告警发去哪。

## 七、覆盖面

4 项，覆盖告警链路的主要安全面。
